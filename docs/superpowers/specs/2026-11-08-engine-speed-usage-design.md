# rauha 엔진: 속도·한도·분석 품질 설계

2026-11-08 · 상태: 초안(사용자 승인 전) · 데스크톱 설계(`2026-11-08-rauha-desktop-design.md`)와 함께 진행

## 1. 왜

사용자가 터미널 rauha를 쓰면서 겪은 문제 네 가지다. 모두 화면이 아니라 엔진(`@rauha/core`)에서 생기므로, 데스크톱으로 옮겨도 그대로 따라온다.

1. 쉬운 질문도 답이 30초쯤 걸린다.
2. 가벼운 질문 하나에 세션 한도가 1~2% 준다.
3. 개발은 잘하지만, 프로젝트와 코드가 커질수록 점점 느려진다.
4. 분석 결과물이 부족하다. 사용자는 분석한 뒤 그걸 바탕으로 코드를 고치는데, 그러려면 brainstorming이나 writing-plans 수준의 결과가 나와야 한다.

## 2. 측정에 대해

한도를 아끼려고 **이번에는 새로 돌리지 않았다(0회)**. 아래 근거는 코드를 따라간 결과와, 이미 있는 실험대 기록(`.rauha/bench/*/bench.md`, 2026-10-25~27, 아주 작은 예제 저장소에서 작은 작업 3종을 돌린 기록)이다.

- 실험대 기록(작은 작업 1건): 1분 8초~2분 54초. haiku 88k~207k 토큰, sonnet 25k~54k 토큰. 마지막 회차(10-27)에서 접수(intake)가 28k~29k, 조사(surveyor)가 0~35k 토큰을 썼다.
- **질문 경로는 실험대에 없어서 측정 기록이 없다.** 그래서 7.1의 "계측 먼저"가 첫 작업이다.

### 2.1 기준 측정 (2026-11-08 시도 — 로그인 만료로 못 함)

측정할 경우는 쉬운 질문 3개, 깊은 질문 2개, 분석 1개, 작은 작업 2개, 모두 8개다. main HEAD(6e7380d)를 분리된 worktree에 빌드하고, 터미널 rauha와 똑같이 대화 세션을 만들어 팀원 호출마다 기록하는 스크립트로 돌렸다.

- **결과: 모든 호출이 첫 단계에서 막혔다.** rauha `personal` 프로필의 로그인이 만료됐다(`OAuth session expired and could not be refreshed`). 모델 토큰은 쓰지 않았다(호출당 0토큰, 1초 안에 끝남).
- **세션 %도 읽히지 않는다.** 같은 프로필에서 SDK 사용률 API가 `rate_limits_available: false`를 돌려준다. 로그인이 풀린 탓으로 보인다. 터미널과 데스크톱의 한도 막대(`readPlanUsage`)도 이 상태에서는 비어 있게 된다.
- **다시 하려면**: 사용자가 `rauha login`(또는 `rauha login --profile personal`)으로 다시 로그인한 뒤 같은 스크립트로 8개 경우를 돌린다. 각 경우 앞뒤로 세션 %도 남긴다. 결과 표는 이 절에 넣는다.

## 3. 지금 호출이 어떻게 나가나

### 3.1 질문 한 번 ("이 함수 어디서 써?")

| 순서 | 호출 | 모델·effort | 붙는 것 | 근거 |
|---|---|---|---|---|
| 0 | (대화 시작 때) 라우터·답변 팀원 프로세스를 미리 띄움 | — | 프로세스만 띄우고 API 호출은 없음 | `chat-session.ts:194-198`, `agent-sdk-team-member.ts:64-74` |
| 1 | 저장소 지식 최신화 → 바뀐 영역이 있으면 **조사 팀원 호출** | haiku·low, 최대 20턴 | 지식 블록(최대 12,000자, 심볼 포함) + 영역 15개 × 파일 40개 목록 | `knowledge.service.ts:38-49, 89-100` |
| 2 | **라우터** | haiku·low, 2턴, 도구 없음, CLAUDE.md 안 읽음 | 라우터 프롬프트(8,071자) + 최근 대화 6턴 + 메시지 | `chat-session.ts:243`, `role-settings.dto.ts:49`, `prompts/router.md` |
| 3 | **답변 팀원** (질문처럼 보이면 2와 동시에 미리 시작) | sonnet·medium, 최대 25턴, 도구 Read·Grep·Glob·WebSearch·WebFetch·Bash, CLAUDE.md 읽음 | 답변 프롬프트(7,020자) + 지식 블록(최대 12,000자) + 대화 + 오늘·지금 시각 + 기억(최대 3,000자) + 질문 | `chat-session.ts:240, 401-428`, `role-settings.dto.ts:52` |
| 4 | 라우터가 "질문 아님"이라 하면 3은 중간에 멈추고 버림 | — | 그때까지 쓴 토큰은 그대로 쓰인 것 | `chat-session.ts:245` |

이 표에서 읽히는 원인은 다음과 같다.
- **쉬운 질문도 sonnet이 여러 턴 도는 일꾼으로 간다.** 답변 팀원은 한 번 답하고 끝나는 게 아니다. 파일을 열 때마다 턴이 하나씩 늘고, 턴마다 시스템 프롬프트, 도구 설명, CLAUDE.md, 지식 블록, 기억이 통째로 다시 들어간다. 캐시가 맞으면 값은 싸지지만 시간과 한도는 계속 쌓인다.
- **코드를 바꾼 뒤 첫 질문은 조사 팀원을 기다린다.** 파일이 하나만 바뀌어도 그 영역이 "낡음"이 되고(`repo-knowledge.ts:122-127`), `current()`가 답보다 먼저 조사를 끝낸다. 개발하면서 질문하면 거의 매번 이렇게 된다.
- **미리 시작한 답변이 버려진다.** 질문처럼 보였는데 라우터가 작업이라고 판정하면, 답변 팀원이 그때까지 쓴 토큰은 버려진다.
- **도구 묶음이 붙으면 미리 띄운 프로세스를 못 쓴다.** 질문에 aws나 브라우저 묶음이 붙으면 미리 띄운 프로세스를 쓰지 않고 새로 띄운다(2초쯤, `agent-sdk-team-member.ts:135-141`).
- **캐시가 자주 식는다.** 사용자가 5분 넘게 쉬었다 물으면 프롬프트 캐시가 식어서 처음부터 다시 쓴다. 지식 블록은 앞쪽에 있어 캐시가 잘 맞는 편이다. 대신 대화 블록과 `<now>`(분 단위로 바뀜)가 그 뒤에 와서, 기억 블록과 질문은 매번 새로 읽는다(`chat-session.ts:415-423`).

### 3.2 작은 코드 수정 한 번 ("Money.add가 빼기를 해, 고쳐줘")

| 순서 | 호출·일 | 모델 | 근거 |
|---|---|---|---|
| 1 | 라우터 | haiku | `chat-session.ts:243` |
| 2 | 지식 최신화(+조사 팀원) | haiku | `minimal-loop.service.ts:232` |
| 3 | **기준 검사 전체**(tests → typecheck → lint를 차례로) — 2·4와 동시 | 모델 없음 | `minimal-loop.service.ts:232`, `node-checks.ts:171-178` |
| 4 | 접수(intake): 업무 지시서 | sonnet·low | `minimal-loop.service.ts:481`, 기록상 28k 토큰 |
| 5 | 테스트 팀원 | haiku(막히면 sonnet) | `:285` |
| 6 | 구현 팀원 | haiku(막히면 sonnet) | `:314` |
| 7 | **검사 전체 다시** (잠근 테스트 + tests·typecheck·lint) — 구현을 다시 할 때마다 | 모델 없음 | `:330` |
| 8 | 리뷰어 | sonnet | `:369` |

**3번 문제(커질수록 느려짐)의 원인은 둘이다.**
- **검사를 매번 전체로 돌린다.** 테스트·타입 검사·린트 전체를 차례로, 기준 한 번에 구현 시도마다 한 번씩 돌린다. 저장소가 커지면 검사 시간이 그대로 늘어나고, 팀원 호출보다 길어진다. 실험대 저장소는 아주 작아서 이 비용이 기록에 거의 안 보였다.
- **조사 팀원이 다시 돈다.** 작업이 파일을 바꾸면 다음 요청 때 조사가 다시 돌고, 큰 저장소일수록 바뀌는 영역도 많다.

### 3.3 분석 요청 한 번 ("결제가 왜 두 번 깎여?")

| 순서 | 호출 | 모델 | 결과 형식 | 근거 |
|---|---|---|---|---|
| 1 | 라우터 → `debug` / `risk` / `ideate` | haiku | — | `chat-session.ts:249-253` |
| 2 | 디버깅·위험 점검·기획 팀원 **한 번** | sonnet·medium (기획은 high) | `{ answer: 문자열, files }` 하나 | `company-desk.ts:62-70`, `schemas.ts:236-244` |

**4번 문제(분석이 부족함)의 원인**: 분석이 호출 한 번에 자유 글 하나로 끝난다.
- 결과 형식에 "원인 후보와 확신도", "고치는 방향 여러 개 비교", "추천과 이유", "단계별 계획"을 담을 자리가 없다.
- 디버깅 프롬프트가 고치는 방법을 "말로 짧게"(`prompts/debugger.md` 4번)로 정해 둬서, 고치기 직전에 필요한 설계와 계획이 나오지 않는다.
- 분석 결과가 그다음 코드 수정 작업의 입력으로 이어지지도 않는다. 사용자가 다시 말로 시키면 접수부터 새로 시작한다.

## 4. 고칠 방향

### 4.1 질문: 가벼운 건 가볍게 (문제 1·2)

| 안 | 내용 | 판단 |
|---|---|---|
| **Q1. 라우터가 바로 답하기** | 라우터 출력에 `quickAnswer`를 더한다. 인사, 시각, 방금 대화에 대한 짧은 되물음처럼 파일을 안 열어도 되는 질문은 라우터 한 번(haiku)으로 끝낸다. | **채택** |
| **Q2. 답변 팀원을 두 등급으로** | 라우터가 `depth: light \| deep`을 낸다. light는 haiku·low, 최대 6턴, 웹 도구 없음, 지식은 질문과 맞는 영역만. deep은 지금처럼 sonnet. 답 아래에 "더 깊게"를 두면 deep으로 다시 묻는다. | **채택** |
| **Q3. 미리 시작 없애기** | 질문처럼 보여도 라우터 판정을 기다린다. Q1·Q2로 쉬운 질문은 haiku라 기다려도 짧고, 버려지는 호출이 없어진다. | **채택**(사용자 결정 2026-11-08) |
| Q4. 조사를 답 뒤로 미루기 | 낡은 영역이 있어도 지금 지식으로 먼저 답하고, 조사는 답한 뒤 쉬는 동안 돌린다. 데스크톱에서는 "저장소 파악" 같은 시스템 작업으로 보인다. | **채택** |
| Q5. 지식 블록을 질문에 맞게 자르기 | 12,000자를 통째로 넣지 않고, 영역 목록 + 질문 낱말과 맞는 영역의 메모·심볼만 넣는다. | **채택** (light만. deep은 지금처럼) |
| Q6. 블록 순서로 캐시 맞추기 | 바뀌지 않는 것(지식) → 천천히 바뀌는 것(기억) → 매번 바뀌는 것(대화, 질문) 순서로 놓는다. `<now>`는 분이 아니라 날짜와 시간대로만 넣는다. | **채택**(작음) |
| 버린 안: 답변 팀원을 늘 haiku로 | 코드를 여러 파일 따라가야 하는 질문의 답이 나빠진다. 사용자는 개발 품질은 만족한다. | 버림 |
| 버린 안: 질문마다 대화를 이어 쓰기(SDK resume) | 턴마다 앞 대화가 다 다시 들어가서 길어질수록 무거워진다. 지금처럼 요약 6턴이 낫다. | 버림 |

**예상 효과** (측정 전 추정. 7.1 계측으로 확인한다)
- 인사나 짧은 되물음: 지금은 라우터 + sonnet 답변(여러 턴), 미리 시작까지 하면 호출 2~3번이다. Q1을 하면 haiku 호출 1번이 된다.
- 가벼운 코드 질문: 지금은 sonnet 여러 턴에 지식 12,000자가 매 턴 들어간다. Q2·Q5를 하면 haiku 몇 턴에 지식 일부만 들어가서, sonnet 토큰이 0이 되고 입력 토큰이 크게 준다.
- 코드를 바꾼 직후의 질문: 답 앞에 기다리던 조사 시간이 빠진다(Q4).

| 버린 안: 검사를 아예 줄이기 | 사용자가 만족하는 "개발 품질"이 검사에서 나온다. | 버림 |

### 4.3 분석: 고치기 직전까지 가는 흐름 (문제 4)

분석을 호출 한 번이 아니라 **네 단계 작업**으로 바꾼다. 각 단계는 앞 단계 결과를 구조화된 데이터로 받는다.

| 단계 | 하는 일 | 누가 | 결과 형식(새 schema) | 사용자 |
|---|---|---|---|---|
| 1. 조사 | 재현, 근거 읽기 | 디버깅·위험 점검 팀원 (sonnet·medium) | 증상, 확인한 사실(파일:줄 근거), 원인 후보(확신도·확인 방법), 모르는 것 | 보기만 |
| 2. 방향 비교 | 고치는 방향 2~3개 | 같은 팀원이 이어서(같은 프로세스, 같은 캐시) | 방향마다 내용, 장단점, 위험, 손댈 곳, 추천과 이유 | **고른다**(또는 다른 방향을 적는다) |
| 3. 설계 | 고른 방향의 설계 | 설계 팀원(지금의 `DesignDesk`) | brainstorming 설계 문서 수준: 목적, 범위, 바뀌는 구조, 엣지 케이스, 버린 안 | 승인 |
| 4. 계획 | 단계별 작업 계획 | 설계 팀원 이어서 | writing-plans 수준: 단계마다 먼저 쓸 테스트, 바꿀 파일, 확인 명령 | "이대로 고치기" |

- **"이대로 고치기"를 누르면 4단계 계획이 그대로 작업 루프의 업무 지시서 입력이 된다.** 지금 `work(..., design)` 인자가 받는 자리다. 접수 팀원이 처음부터 다시 파악하지 않는다.
- **멈출 곳을 고를 수 있다.** 원인만 알고 싶으면 1단계에서 끝난다. 라우터가 요청을 보고 어디까지 갈지 고르고("원인이 뭐야" → 1, "어떻게 고치지" → 2, "고쳐줘 전에 분석" → 4), 사용자가 화면에서 이어 갈 수 있다.
- **2단계에서 고른 결과는 기록이 된다.** 어느 방향이 AI 추천이었고 사용자가 무엇을 골랐는지가 데스크톱 덩어리 3의 기록 탭에 그대로 남는다. 사용자의 포트폴리오 목적과 바로 맞물린다.
- **한도**: 지금은 sonnet 1번이다. 1~2단계는 sonnet 1~2번이고, 2단계는 같은 프로세스에서 이어 가서 캐시가 맞는다. 3~4단계는 sonnet 1~2번 더 든다. 끝까지 가면 **지금의 약 2~4배**다. 대신 "분석 → 다시 설명 → 작업 접수 → 다시 파악"으로 반복되던 호출이 빠진다. 1단계에서 멈추면 지금과 같다.
- **3단계 모델**(사용자 결정 2026-11-08): 기본은 sonnet·high다. 큰 변경일 때만 Opus를 쓴다. 큰 변경은 여러 저장소에 걸치거나, 1단계가 짚은 영역이 셋 이상이거나, 라우터가 feature로 본 경우다.

## 5. 데스크톱 작업(Job)과 맞물림

- **질문**: light 질문은 작업을 만들지 않는다. 메인 칸에서 바로 답한다. deep 질문과 분석은 작업이 되어 팀 방이 생긴다.
- **분석 네 단계 = 작업 하나의 진행 단계**다. 2단계 "방향 고르기"는 작업 상태 "내 선택 기다림", 3단계 승인은 "허락 기다림" 화면(정리 보기)에 그대로 들어간다.
- **조사 팀원의 배경 실행은 시스템 작업이다.** 팀 방은 안 만들고 상태 줄에 "저장소 파악 중"만 보인다. 동시 실행 상한(3)에 넣지 않고, 쉴 때만 돈다.
- **계측(7.1)은 작업 화면의 "걸린 시간"과 같은 데이터를 쓴다.** 단계별 시간과 호출 수가 팀 상세의 진행 단계 옆에 보인다. 돈 대신 토큰과 %로 보여 준다.
- 데스크톱 개발 담당이 `ChatSession`을 메인 대화와 작업으로 쪼개는 중이다. 그래서 이 문서의 코드 변경은 **그 쪼개기가 main에 들어간 뒤** 새 구조 위에 한다.

## 6. 하지 않을 것 · 실패로 볼 것

- 측정 없이 "빨라졌다"고 말하는 것. 7.1 계측 전후 숫자로만 말한다.
- 개발 품질을 깎아서 빨라지는 것. 검사 생략이나 리뷰 생략이 여기에 해당한다.
- light 답이 틀렸는데 "더 깊게"로 갈 길이 없는 것.
- 분석 네 단계가 사용자 선택 없이 끝까지 자동으로 가서 한도를 쓰는 것.

### 8.1 문서만 고치는 요청 (실제 호출 2번)
