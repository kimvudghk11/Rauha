# 여러 저장소를 한 번에 고치기 — 설계

- 날짜: 2026-11-03
- 상태: 1단계 구현(2026-11-03). 사용자 확인: "순서를 정해서 먼저 만들어져야 하는 걸 만들고 하는 식이면 괜찮다".
- 구현: `RepoPlan`(도메인), `RepoPlanDto`·`ContractCheckDto`, `ManyRepoDesk`, 역할 `splitter`(`prompts/splitter.md`), 결과 `TurnOutcome` kind `repos`.
- 출발점: 사용자 요청 "여러 프로젝트를 동시에 분석해서 해도 문제 없이 빠르게 각 레포를 다 잘 분석해서 수정하면 좋겠어. 여러 개를 건드려도 완벽함을 올리는 rauha".

## 지금 상태 (코드에서 확인한 것)

- 여러 저장소를 **읽는** 일은 된다. `WorkspaceSession.handle`이 요청에서 저장소를 고르고(`workspace.pick`), 첫 저장소의 `ChatSession.handle(input, also)`에 나머지를 `also`로 넘긴다. 질문은 `additionalDirectories`로 함께 열고, 문서 작업도 `also`를 받는다.
- **고치는** 일은 막혀 있다. `chat-session.ts`의 `MANY_REPO_WORK`("여러 저장소를 한 번에 고치는 일은 아직 하지 않아요…")를 work·feature·/design에서 돌려준다.
- 저장소마다 묶음(`Bundle`: 프로필, ChatSession, 팀, 기억)이 따로 있다(`packages/cli/src/chat/repo-sessions.ts`). 작업 잠금은 폴더마다 하나다(`FileWorkLock`). 그래서 저장소별 작업은 서로 막지 않고 동시에 돌 수 있다.
- 다른 계정(프로필)의 저장소를 섞은 요청은 이미 거절한다. 이 규칙은 그대로 둔다.

## 목표

- 한 요청이 여러 저장소의 코드를 바꿔야 하면(예: "주문 API에 쿠폰 필드 추가하고 웹이랑 앱에서도 보여줘") rauha가 저장소마다 할 일을 나누고, 서로 맞아야 하는 약속을 먼저 정한다. 약속은 API 경로, 요청·응답 필드, 이벤트 이름, 공유 타입 같은 것이다.
- 서로 기다릴 필요가 없는 저장소는 동시에 고친다.
- 끝나면 저장소 사이의 약속이 실제 코드에서 양쪽 다 맞는지 한 번 더 검사한다.
- 결과는 저장소별로 무엇이 바뀌었고 무엇이 멈췄는지 한 화면에 보여 준다.

## 하지 않을 것

- 커밋, push, 배포는 하지 않는다. 지금과 같다.
- 한 저장소가 실패했을 때 다른 저장소의 변경을 되돌리지 않는다. 결과 화면에 어느 저장소가 바뀌었는지 분명히 보여 주고, 판단은 사용자가 한다.
- 다른 계정의 저장소를 섞지 않는다.
- 저장소 수에 상한 없이 동시에 돌리지 않는다.

## 흐름

1. **나누기** (sonnet 1회, 새 역할 `splitter`, 읽기 전용, 대상 저장소들을 모두 `additionalDirectories`로 연다). 저장소 지식이 있으면 함께 넘긴다. 출력은 아래와 같다.
   - `parts`: 저장소 이름, 그 저장소에 시킬 요청 한 덩어리, `dependsOn`(먼저 끝나야 하는 저장소)
   - `contract`: 저장소 사이에 맞아야 하는 약속 목록. 각 항목에 무엇이, 어느 저장소들 사이의 약속인지, 정확한 모양(경로·필드·타입)을 적는다.
   - `edgeCases`: 저장소 경계에서 생기는 엣지 케이스(구버전 클라이언트, 필드 없음, 배포 순서 차이)
   - 바꿀 게 없는 저장소는 `parts`에서 뺀다. 약속을 코드에서 확인할 수 없으면 질문으로 돌린다(설계 대화와 같은 `discuss`).
2. **실행**. 저장소마다 그 저장소의 `ChatSession.work(part, …)`를 부르고, `<contract>` 블록을 접수 팀장에게 넘긴다. 접수·테스트·구현·리뷰는 지금 최소 루프 그대로 돈다. `dependsOn`이 없는 저장소부터 동시에 시작한다(동시에 최대 3개). 앞 저장소가 멈추면 그것에 기대는 저장소는 건너뛴다(`Design.isBlocked`와 같은 규칙).
3. **약속 검사** (sonnet 1회, 리뷰어 역할을 저장소 사이 검사용 입력으로 부른다). 바뀐 파일과 `contract`를 보고, 약속마다 양쪽 코드의 줄을 근거로 맞는지 판정한다. 어긋나면 그 저장소에 고칠 작업을 한 번만 더 넣는다(승격 사다리 대신 1회로 제한).
4. **결과**. 저장소별 결과 카드(바뀐 파일, 테스트, 멈춘 이유)와 약속 검사 결과를 보여 주고, 기억에는 저장소마다 작업 기억을 남긴다.

기능 요청(feature)이 여러 저장소에 걸치면 1단계 앞에 설계 대화를 한 번 한다. 설계의 `tasks`에 저장소 이름을 붙이는 방식으로 넓히는데, 이건 2단계 구현으로 미룬다.

## 동시에 돌 때의 화면

- 진행 줄은 저장소 이름을 앞에 붙인다(`[shop-api] 테스트 작성 중…`).
- 사용자에게 묻는 일(해석 고르기, 위험 명령 허락, 사실 확인)은 한 번에 하나만 보인다. `UserPort`와 `PermissionAsker`를 줄 세우는 래퍼로 감싸고, 질문 앞에 저장소 이름을 붙인다. 기다리는 동안 다른 저장소의 작업은 계속 돈다.
- 알림은 지금처럼 4초 안에 답이 없으면 OS 알림을 띄운다(`notifyWhile`).

## 호출 수와 모델 (세션 절약)

- 저장소 N개 요청 = 나누기 sonnet 1 + 저장소별 최소 루프 N개 + 약속 검사 sonnet 1. 저장소별로 따로 요청했을 때보다 호출이 2회 많다. 대신 약속이 어긋나서 다시 일하는 경우를 줄인다.
- 저장소 지식은 저장소가 4개를 넘으면 지금 규칙(`ALSO_KNOWLEDGE_MAX`)대로 이름만 넘기고 필요한 파일만 연다.

## 정한 것

- 사용자가 정함: 나누기에서 먼저 만들어야 하는 저장소(dependsOn)를 정하고, 그 저장소가 끝까지 해낸 뒤에 기다리던 저장소를 시작한다. 기다릴 것이 없는 저장소끼리만 함께 돈다.

## rauha가 정한 것

- 동시에 최대 3개 저장소. 넷 이상이면 줄을 세운다.
- 실패한 저장소의 변경은 되돌리지 않는다(사용자가 git으로 판단).
- 약속 검사에서 어긋나면 고치기는 1회만.

## 위험과 확인하지 못한 것

- 동시에 도는 최소 루프 여러 개가 구독 한도를 빠르게 쓴다. `SessionBudget`이 빠듯하면 동시 실행을 1개로 줄인다.
- 저장소마다 다른 테스트 명령·언어를 쓰면 저장소별 최소 루프는 그대로 되지만, 약속 검사는 코드 읽기에만 기댄다(양쪽을 함께 돌리는 통합 테스트는 하지 않는다).
- 터미널에서 동시 진행 줄이 깨지지 않는지 Windows cmd와 VS Code 터미널에서 확인해야 한다.
