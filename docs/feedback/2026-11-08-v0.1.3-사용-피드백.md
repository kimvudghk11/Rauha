# v0.1.3 사용 피드백과 처리 계획 (2026-11-08)

사용자가 v0.1.3을 직접 쓰고 남긴 아쉬운 점이에요. "원인"은 코드를 읽고 세운 **가설**이고, 확인하면 이 문서를 고쳐요. 사실과 가설을 나눠 적었어요.

## 1. 아래 상태 줄의 세션 %가 실시간이 아니에요 (처리함, 코드 확인 2026-11-08)

- **증상**: 화면 맨 아래 상태 줄의 세션(5시간) %와 설정 창의 세션 %가 달라요. 설정 창이 더 최신이에요.
- **확인한 원인(사실)**: 처음 가설("설정은 열 때 새로 읽는다")은 **틀렸어요.** 설정 창도 상태 줄과 똑같이 `usage:get`으로 main이 저장해 둔 값을 받았어요. 차이는 **저장값을 언제 받아 가느냐**였어요. main은 1분마다 읽어 저장하고, 상태 줄 화면은 30초마다 그 저장값을 가져와 그렸어요(읽는 간격과 가져오는 간격이 따로 돌아 최대 약 90초 늦음). 설정 창은 열 때 가져오니 그 순간의 최신 저장값이라 더 새로웠어요. 그리고 읽기에 실패하면 예전 값을 조용히 남겨서 오래된 값인지 알 수 없었어요.
- **한도 읽기 호출의 비용(사실)**: `readPlanUsage`는 Agent SDK `query`에 프롬프트를 보내지 않는 세션을 만들고 `usage_EXPERIMENTAL…({ skipBehaviors: true })`로 /usage와 같은 구독 사용률만 묻는 호출이에요. 모델을 부르지 않고 대화 기록도 훑지 않아요(코드 주석 기준 약 1.6초, 달러 0). Claude 실행 파일을 잠깐 띄우므로 CPU는 쓰지만 한도(토큰)를 쓰는 호출은 아니에요. 이번 작업에서는 실제 Claude를 부르지 않아서 한도 소모 0은 SDK 설명과 기존 측정 주석에 근거한 값이고, 새로 재지는 않았어요. SDK에서 실험 중인 기능이라 바뀌거나 사라질 수 있어요(그러면 null).
- **고친 것**: 읽는 곳을 `UsageService`(main/usage) 하나로 합쳤어요. 상태 줄·설정·새 작업 시작 판단이 모두 이 값을 받아요. 값이 새로 읽히면 main이 화면에 밀어 줘서(`usage:changed`) 상태 줄과 열려 있는 설정 창이 같이 바뀌어요. 평소 25초, 설정을 열 때·창에 초점이 돌아올 때(5초 안 중복은 건너뜀)·일이 끝날 때 즉시 읽고, 읽는 중에 온 요청은 합쳐요(일이 끝났을 때는 끝난 뒤 한 번 더). 읽기에 실패하면 예전 값과 **읽은 시각을 그대로** 둬서 오래됨이 드러나요. 상태 줄 한도에 마우스를 올리면 "한도를 읽은 시각: n초 전"(75초 넘으면 오래된 값 표시), 설정 한도 칸에도 같은 글이 있어요. 계정 설정을 바꿔도 다음 읽기부터 새 계정으로 읽어요(예전엔 시작할 때 고른 계정에 고정). 규칙은 `shared/usage-freshness.ts`(spec 12개), 합치기는 `usage-service.spec.ts`(6개).
- **끝났다는 기준**: 상태 줄과 설정이 같은 저장값 하나를 받으므로 같은 순간에는 차이 0%p. 확인은 단위 테스트까지 했고, 화면을 띄운 확인은 하지 못했어요(아래 "못 한 것").

## 2. 로그인 계정 표시와 로그인 버튼 (처리함)

- **증상**: 로그인한 계정을 보여 주는 칸이 환경에 따라 "다시 로그인해야 하는 것처럼" 보여요.
- **확인한 원인(사실, 코드와 실제 `claude auth status` 실행으로)**:
  1. **로그인돼 있어도 항상 큰 파란 "다시 로그인" 버튼**이었어요(`btn primary`, 로그인됨이면 글자만 "다시 로그인"). 모든 환경에서 재로그인을 요구하는 것처럼 보인 직접 원인이에요.
  2. **앱의 기본 계정 폴더는 `~/.rauha/profiles/personal/claude`**예요(`config.toml`이 없을 때의 기본 프로필). 터미널의 Claude Code(`~/.claude`)에 로그인해 둔 사람이 앱을 열면 다른 폴더를 보니 "로그인되어 있지 않아요"가 나와요. 새 폴더로 `auth status`를 돌려 보면 `loggedIn:false`, 종료 코드 1, JSON 출력이었어요. 맥·윈도우 모두 같아요. 어느 폴더를 보는지 화면에 안 나와서 이유를 알 수 없었어요.
  3. **"확인 못 함"과 "로그인 안 됨"이 구분되지 않았어요.** 시간 초과(10초)·실행 실패·깨진 출력·계정 설정 읽기 실패가 모두 `null`로 뭉개져서 이유 없이 "확인하지 못했어요"와 큰 로그인 버튼이 같이 나왔어요. 계정 설정 파일이 깨진 경우는 예외가 그대로 새어 나갔어요.
  - 맥 Finder 실행: 앱이 PATH의 claude를 쓰지 않고 앱에 든 실행 파일을 절대 경로로 쓰고(`claudeBinaryPath`) 시작할 때 로그인 셸 PATH를 합치므로(`adoptShellPath`) PATH 부재는 원인이 아니에요. 맥 키체인 동작은 맥이 없어 직접 확인하지 못했어요(못 한 것).
- **고친 것**: 계정 구역을 세 상태로 나눴어요(`shared/account-state.ts`, spec 14개, `ClaudeLogin.check()` spec 4개 추가). 누구로 로그인됨(`auth status`의 이메일 → 없으면 로그인 방식, 조직·요금제와 계정 폴더 경로를 홈은 ~로 줄여 함께 표시) / 로그인 안 됨(`loggedIn:false`라고 분명히 답한 때만, 이 앱 계정 폴더는 터미널 로그인과 따로라는 안내 포함) / 확인 못 함(이유 한 줄: 실행 파일 없음·시간 초과·실행 실패·종료 코드와 마지막 오류 줄·깨진 출력·설정 읽기 실패, 노란 표시, "다시 확인" 버튼). 로그인 버튼은 "로그인 안 됨"일 때만 파란색으로 크게, 그 밖에는 작은 "다른 계정으로 로그인". 설정 맨 위 계정 카드 하나로 모았고 첫 실행 3단계는 같은 부품을 써요. 오류 카드는 로그인이 필요한 상황이라 버튼만 보여요. 창에 초점이 돌아오면 상태를 다시 읽어요. 토큰은 읽지도 옮기지도 않고 `auth status`의 JSON 출력만 읽어요.
- **끝났다는 기준**: 로그인된 환경에서는 작은 보조 버튼만 보이고, 상태 확인에 실패하면 이유가 보여요(단위 테스트로 확인).

## 못 한 것 (1·2번)

- 창을 띄운 화면 확인과 스크린샷(숨김 창 스크린샷 모드 포함)은 하지 않았어요. 단위 테스트와 typecheck까지만 확인했어요.
- 맥(Finder 실행, 키체인)에서의 실제 동작은 확인하지 못했어요. 로그인된 계정으로 `auth status`를 돌려 이메일 필드가 실제로 나오는지는 확인하지 못했고(실행 파일 코드의 출력 필드 `email`·`orgName`·`subscriptionType`을 읽어 맞췄어요), 못 읽으면 로그인 방식 이름으로 보여요.
- 기본 계정 폴더를 `~/.claude`로 바꿀지(터미널 로그인을 그대로 쓰기)는 계정 분리 정책이라 정하지 않았어요. 사용자 결정이 필요해요.

## 4. UI/UX 전면 정리 (버튼 위치·글자 위치가 안 맞음)

- **증상**: 곳곳에서 버튼 위치, 버튼 안 글자 위치(세로·가로 정렬), 크기가 서로 달라서 어색해요. git 탭은 push만 파란색이고 나머지는 어두운 회색이라 일관성이 없어요.
- **가설**: 탭마다 다른 담당이 만들어서 버튼·간격·정렬 규칙이 탭별 CSS에 따로 있어요(`styles.css`, `chat.css`, `git.css` 등 클래스가 섞여 있고 같은 이름이 겹친 적도 있음).
- **하기로 한 방식**:
  1. **화면 구조도 다시 그리기**: 지금 앱의 모든 화면(탭 12개 안팎, 설정, 첫 실행, 팀 상세, 허락 카드, 알림, 업데이트 배너, 제목줄)을 실제 코드와 스크린샷으로 전수 조사해 "화면 → 영역 → 부품" 구조도를 `docs/design/ui-structure.md`에 그려요. 시안이 아니라 **지금 있는 그대로**를 그리고, 어긋난 곳에 표시해요.
  2. **공통 디자인 규칙 뽑기**: 색(기본/강조/위험/보조 버튼), 버튼 높이·안쪽 여백·글자 세로 가운데, 아이콘 버튼 크기, 간격 단계(4·8·12·16), 글자 크기 단계, 카드·목록 행·입력칸·탭·배지·토스트 부품을 `docs/design/ui-components.md`와 공통 CSS 한 파일(토큰과 부품)로 정해요.
  3. **모든 탭을 공통 부품으로 갈아끼우기**. 탭마다 고유 버튼 CSS를 없애요.
  4. **확인**: 4단계 폭(1700·1100·720·그 아래)에서 화면별 스크린샷으로 정렬을 검사하고, 버튼 높이·글자 정렬을 자동으로 재는 테스트(같은 종류 버튼의 높이·패딩이 같다)를 넣어요.
- **git 탭 색 규칙**: 가장 중요한 한 동작만 강조색(파란색), 나머지는 보조 버튼. push/pull/fetch/commit이 서로 다른 색 체계로 보이지 않게 해요.
- **끝났다는 기준**: 같은 종류의 버튼은 어느 탭에서나 같은 높이·글자 위치·색이에요. 구조도 문서가 실제 화면과 일치해요.

## 5. git 자동화: 자동 commit → PR → merge, **qa 브랜치로만**

- **하려는 것**: 작업이 끝나면 앱이 변경을 자동으로 commit하고, PR을 만들고, **qa 브랜치로만** merge해요.
- **안전 규칙(바꾸지 않아요)**:
  - 대상은 qa(설정에서 고른 "자동 merge 대상 브랜치")뿐이에요. main·release 같은 보호 브랜치로는 자동으로 가지 않아요. 비밀 파일 차단과 `git push` 거절 규칙은 그대로예요(앱이 사용자 이름으로 하는 push와 팀원이 하는 push는 다르게 다뤄요).
  - 처음에는 **허락 카드를 거쳐요**(코드 diff, qa에 주는 영향 표). "이 레포·이 작업 동안 자동으로 허락"을 켜면 카드 없이 진행해요. 기본값은 꺼짐.
  - 브랜치 이름·커밋 제목은 그 레포의 기존 방식을 따라요(이미 만든 규칙 읽기 재사용).
  - qa로 merge하기 전에 충돌이나 CI 실패가 있으면 멈추고 알려요.
- **열린 질문(사용자 확인 필요)**: PR 만들기와 merge는 GitHub 로그인이 필요해요. 이 앱은 Claude 토큰은 만지지 않지만 GitHub는 `gh`(GitHub CLI) 로그인이나 개인 토큰이 필요해요. 어떤 방식을 쓸지(`gh` 로그인을 앱이 확인만 하는 방식을 추천) 정해야 해요. GitLab·사내 Git 서버는 어떻게 할지도.
- **끝났다는 기준**: qa 브랜치만 가능하고 다른 브랜치로는 못 가요. 허락 카드에 영향이 보여요. 충돌·실패 시 멈춰요. 단위·git 통합 테스트로 검증해요.

## 처리 순서와 담당

1. 터미널 칸 마무리(코드 탭 담당).
2. 피드백 1·2번(한도 읽기 통합, 계정 구역).
3. 0.1.4 릴리스.
4. UI 전수 조사·구조도 → 공통 부품 → 탭 갈아끼우기.
5. git 자동화(위 열린 질문 답을 받은 뒤).

각 업데이트는 "공격적 점검 → 개선 → 추가 테스트" 순서로, 직전 릴리스를 실제로 돌려 본 결과를 기준으로 해요.

## 6. 트러블슈팅 블로그 글 만들기 (사용자 추가 요청, 2026-11-08)

- **요청**: 포트폴리오·이력서용 글이 아니라, 겪은 트러블슈팅을 **블로그 글로 써 주거나, 글을 쓰기 위해 정리해 주는 기능**. 기능은 미리 다 만들어 두기.
- **어디에**: 기록 탭(이미 트러블슈팅·네트워크·인프라 태그와 "문제 → 접근 → 방향 → 결과" 마크다운 복사가 있음)에서 기록 하나 또는 여러 개를 골라 "블로그 글" 버튼.
- **두 방식**:
  1. **정리 노트(모델 호출 없음)**: 기록의 요청·단계·허락 결정·결과·바뀐 파일에서 글감을 뽑아 `문제 상황 / 원인 추정 / 시도한 것(실패 포함) / 해결 / 배운 점 / 재현·확인 방법` 뼈대에 채우고, 비어 있는 칸은 "직접 채우기"로 표시한다(지어내지 않는다).
  2. **초안 쓰기(문서 팀원 잉크, 모델 1회)**: 정리 노트를 바탕으로 블로그 어투(사용자가 고른 톤: 담백/친근)의 초안을 쓴다. 호출 전에 "모델을 한 번 부른다"고 알리고 눌러야 실행한다.
- **공개 글이므로 가림이 핵심**: 회사·사내 이름, 레포 이름, 도메인·IP·계정 번호·리전·토큰·이메일을 기본으로 일반 이름으로 바꾼다(미리 보기에서 바꾼 목록을 보여 주고 사용자가 되돌릴 수 있다). 코드 조각은 사용자가 고른 것만 넣고, 비밀 파일 내용은 절대 넣지 않는다.
- **내보내기**: 클립보드 복사, `.md` 파일로 저장(폴더는 사용자가 고름), 제목·태그 후보 3개, 글 길이 선택(짧게/보통/자세히).
- **끝났다는 기준**: 가림 목록이 테스트로 고정돼 있고(사내 이름·IP·키가 결과에 안 남음), 정리 노트는 모델 호출 0회, 초안은 사용자 확인 뒤 1회. 기록이 비어 있으면 "글감이 없어요"로 안내.
- **순서**: 분석 4단계(선택 기록)와 같은 기록 데이터를 쓰므로 그 뒤에 만들되, 정리 노트(1번 방식)는 지금 기록만으로 먼저 만들 수 있다.
